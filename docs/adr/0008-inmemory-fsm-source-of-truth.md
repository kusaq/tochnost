# ADR-0008. In-memory FSM — источник правды

**Статус:** принято · **Инвариант:** INV-8

## Контекст
Система работает в реальном времени с потоком двух контуров датчиков. Нужен единый непротиворечивый взгляд на «что сейчас на конвейере», устойчивый к гонкам и к переупорядочиванию пакетов.

## Решение
- **`SENSOR_STATE` (in-memory) = истина** о текущем конвейере (`active`, `waiting_at_post2`, `Post2Tracker`, `_tightening`). Все переходы под `fsm_lock()`.
- **TimescaleDB** — персистентность (история, отчёты, восстановление), не оперативный источник правды.
- **Redis** — только транспорт для live-дашборда (pub/sub), не источник правды.
- **Stream Monitor** — диагностический буфер, на FSM не влияет.
- Единая очередь `merged_queue` сливает S1+S2 в хронологию с буфером `REORDER_BUFFER_MS` (500 мс).
- При рестарте `rehydrate_in_progress_rails()` поднимает единственную `IN_PROGRESS` из БД.

## Последствия
- Быстрые и консистентные решения FSM без обращений в БД на горячем пути.
- Состояние конвейера теряется при падении процесса, кроме одной `IN_PROGRESS` (восстанавливается). Долгую историю искать в БД.
- Нельзя «чинить» состояние правкой БД в обход FSM.

## Отвергнутые альтернативы
- *БД как источник правды в реальном времени* — латентность, гонки на горячем пути.
- *Redis как истина* — эфемерность, не для консистентных переходов.

## Где в коде
`tochnost/src/api/v1/sensor/state.py` (`SENSOR_STATE`), `service.py` (`fsm_lock`, `_sensor_merged_worker`, `rehydrate_in_progress_rails`).
