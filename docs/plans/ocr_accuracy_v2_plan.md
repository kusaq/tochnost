# План: читать маркировку РШР «супер чётко»

## 1. Что мы читаем

На лице шпалы **от руки красной краской**:

```
Фоссло   1809-50   УК.80
   │        │  │      │
   │        │  │      └── тип (словарь: УК.80 / L.XX.XX)
   │        │  └───────── эпюра, расстояние между шпалами (в основном 50)
   │        └──────────── номер РШР — ИТЕРИРУЕТСЯ (+1, иногда с пропусками)
   └───────────────────── производитель (словарь: ФОССЛО)
```

Это не печатный OCR, а **рукописный текст в дикой среде**: кисть, шершавый бетон,
выцветание, рыбий глаз Hikvision, съёмка под углом. Символы ~30 px.

**Порядок токенов непостоянен** — рабочие пишут как придётся. Проверено:
`Фоссло 1809-50 УК.80` на одной РШР и `УК.80 1812-50 ФОССЛО` на другой.

---

## 2. Главная идея плана

> Номер **итерируется**. Значит система не обязана его *читать* — ей достаточно
> *подтвердить ожидаемый следующий*. Верификация кратно легче распознавания.

Из четырёх полей маркировки три — словарные (`ФОССЛО`, `УК.80`/`L.XX.XX`, эпюра
почти всегда `50`). Единственная свободная величина — 4-значный номер, но и он
предсказуем на шаг вперёд. При грамотном использовании этой структуры даже
посредственное посимвольное качество даёт почти безошибочный результат.

Это и есть ответ на «как читать супер чётко»: **не читать сильнее, а перестать
читать в вакууме**.

## 3. Диагноз: замеры на текущих данных (2026-08-03)

| Что проверено | Результат |
|---|---|
| Объём данных | **5 РШР / 36 кадров**, test = 2 РШР |
| Ошибки в разметке | **1 папка из 5**: в `ФОССЛО 1810-50 УК.80` краской написано **1809** |
| **Фиксированный ROI** | `ROI_Y=(0.57,0.70)`, а на 17/36 кадров текст на **y≈0.88** → **полный промах** |
| Разрешение кадров | **разное**: 1920×1080 и 2688×1520 |
| Высота символов | ~30 px (нижняя граница для rec-моделей) |
| Координаты боксов | **выбрасываются** в `parse_paddle_results` → порядок токенов ломается |
| Грамматика номера | переобучена на `18XX-50`, не видит `2412-30`, режет `1899-51` → `1899-5` |
| Цифры в почерке | видели только `0 1 2 4 5 8 9` — **3, 6, 7 не видели ни разу** |
| Красная маска | ловит перила и оранжевую машину, но с гейтом по шпале **чисто берёт строку** |

### Три подтверждённых дефекта

**Д1 — локализация промахивается.** Самый весомый. Фиксированный ROI подобран под
один ракурс; на кадрах, где РШР ближе к камере, маркировка уходит вниз кадра и в
ROI не попадает вовсе. На таких кадрах OCR смотрит на пустой бетон. Это, вероятно,
значимая часть наблюдаемого «кривовато».

**Д2 — метрика врёт.** Папка названа `1810-50`, на бетоне `1809-50`. Модель читала
**правильно**, eval засчитывал ошибку. «57% EM» — измерение сломанной линейкой на
выборке из двух РШР.

**Д3 — порядок токенов.** `parse_paddle_results` ([ocr_pipeline.py:251](collect_Data/ocr_pipeline.py:251))
теряет bbox; порядок восстанавливается по **вертикальным** зонам, хотя токены стоят
**горизонтально**. Отсюда `УК.80 1809-50 ФОССЛО` вместо `ФОССЛО 1809-50 УК.80`.

## 4. Ограничения (согласованы)

| Ограничение | Следствие для плана |
|---|---|
| Камеры трогать нельзя, **только программно** | ~30 px — это потолок оптики; берём своё мультикадром и локализацией |
| **Сохранение кадров включить можно** | главный блокер снят: данные копятся сами, без поездок |
| Оператор — **только постфактум** | вместо realtime-подтверждения → очередь разбора в конце смены |
| При неуверенности — **лучшая догадка + пометка** | поле всегда заполнено, но с флагом доверия |
| **GPU есть** | дообучение и генеративная синтетика доступны |
| Наряда с ожидаемыми номерами **нет** | последовательность выводим сами из серии чтений |
| Номера итерируют **с пропусками** | трекер должен допускать скачки вперёд |
| Эпюра — в основном 50, иногда меняется | маленький словарь + сильный приор |

**Важное следствие «постфактум».** Это не только ограничение, но и возможность:
раз ответ не нужен мгновенно, можно применять **обратное сглаживание** по всей
смене. Если прочитано `1808, ?, 1810`, то середина почти наверняка `1809` — знание
из будущего исправляет прошлое. Offline-сглаживание точнее online-фильтрации.

## 5. Архитектура: слои

```
Кадр
 └─ Слой 1: Локализация по краске   → тугой кроп + x-координаты + отбраковка
     └─ Слой 2: Распознавание       → rec-модель (дообученная на GPU)
         └─ Слой 3: Грамматика      → XXXX-XX + словари токенов и эпюры
             └─ Слой 4: Мультикадр  → голосование по кадрам одной РШР
                 └─ Слой 5: ПОСЛЕДОВАТЕЛЬНОСТЬ → приор +1, сглаживание по смене
                     └─ Слой 6: Неуверенность → флаг → разбор → golden labels
```

Каждый слой убирает свой класс ошибок и дешевле следующего.

### Слой 1. Локализация по красной краске — чинит Д1

Заменить фиксированный ROI на поиск текста **по цвету краски**. Проверено на ваших
кадрах: красная маска + пространственный гейт по лицу шпалы + фильтр по размеру
компонент чисто выделяет строку, отсекая перила и оранжевую машину.

Даёт одним куском:
1. **Находит текст там, где он есть** — снимает промах на половине кадров.
2. **Тугой кроп** → выше эффективное разрешение для rec.
3. **x-координаты токенов** → правильный порядок (чинит Д3 бесплатно).
4. **Отбраковка кадра**: нет строки буквоподобных компонент → РШР не в позиции,
   кадр не голосует. Плюс детект обрезки текста краем кадра.
5. **Независимость от разрешения** — работает и на 1080p, и на 1520p.

Улучшения против текущей `red_mask` в [diagnose_roi.py:29](collect_Data/diagnose_roi.py:29):
краснота как `R − max(G,B)` или канал `a*` из LAB вместо жёсткого HSV (текущие
пороги **фрагментируют** выцветшие штрихи), морфологическое замыкание, кластеризация
компонент в строку.

### Слой 2. Распознавание

- Починить `parse_paddle_results` — **сохранять bbox**.
- **Дообучение rec на GPU** на реальных кропах (инфраструктура есть:
  `prepare_rec_dataset.py`, `train_rec.sh`, `models/rail_rec_infer`).
- **Синтетика — точечно, под пробел в данных.** Банк реальных глифов из своих же
  кадров даёт идеальный домен, но в нём **нет цифр 3, 6, 7**. Именно туда и нужна
  генерация (шрифты/диффузия на GPU) — закрыть дыру, а не заменять реальные данные.
  Текущий `gen_synth.py` рисует шрифтами macOS (SignPainter, Brush Script) — на
  почерк рабочего они не похожи, это фолбэк, а не основа.

### Слой 3. Грамматика и словари

- **Расширить номер** с `1[78]\d\d-5[0О]` до общего `\d{4}-\d{2}` — иначе РШР
  другого типа не читается вовсе. Жёсткое ограничение на структуру, мягкий приор
  на значения.
- **Эпюра** — словарь наблюдённых значений (в основном `50`), снеппинг к ближайшему.
- **ФОССЛО / УК.80 / L.XX.XX** — словарные токены, уже решены (100%).

### Слой 4. Мультикадровая фузия

`aggregate_series` **уже написан** ([ocr_pipeline.py:413](collect_Data/ocr_pipeline.py:413)),
но **не подключён** ни к eval, ни к рантайму.

- Группировка кадров по РШР: в eval — по `source_folder`, в рантайме — по границам
  стоянки на посту (их знает FSM).
- Голос взвешивать **качеством кадра**: резкость кропа, площадь маски, число
  найденных компонент — а не только `conf`.
- Раз оптику менять нельзя, здесь же имеет смысл **мультикадровое сверхразрешение**:
  сложение десятков субпиксельно смещённых кадров повышает эффективное разрешение
  текста без вмешательства в железо.

### Слой 5. Трекер последовательности — ядро точности

Наряда нет, поэтому последовательность выводим из самих чтений.

- **Модель перехода**: `+1` с высокой вероятностью, `+k` (пропуск) — с меньшей,
  произвольный скачок (новая партия) — с малой. Параметры оценить по накопленным данным.
- **Модель наблюдения**: посимвольная матрица ошибок OCR (какие цифры с какими
  путаются в этом почерке) — строится из данных разбора.
- **Декодирование**: forward-backward / Витерби по всей смене. Это и есть обратное
  сглаживание: `1808, ?, 1810` → середина почти наверняка `1809`.
- **Детект разрыва**: если OCR уверенно и на нескольких РШР подряд противоречит
  прогнозу — это смена партии, надо переякориться, а не «чинить» чтение.

Здесь основной прирост. Даже при среднем посимвольном качестве последовательность
плюс мультикадр дают почти безошибочный номер.

### Слой 6. Неуверенность и разбор

- Писать **лучшую догадку + флаг доверия** (как решено), не NULL.
- Очередь постфактум-разбора: РШР с низкой уверенностью или конфликтом
  «OCR vs прогноз последовательности» — наверх списка.
- Каждое решение оператора → **golden label**, автоматически в обучающую выборку.
  Система учится на собственной эксплуатации.

## 7. Метрика приёмки

Единица — **РШР**, не кадр. Сравнение — **order-independent** (`parts_match` уже
есть, [ocr_pipeline.py:246](collect_Data/ocr_pipeline.py:246)): порядок токенов на
бетоне непостоянен и заводу не важен, важен набор `{ФОССЛО, 1809-50, УК.80}`.

Отдельно измерять:
- accuracy **номера** (единственное свободное поле);
- accuracy **до** и **после** трекера последовательности — чтобы видеть его вклад;
- **долю флага «не уверен»** и точность внутри уверенной части.

Целевая формулировка — точность при покрытии: ~95% РШР без флага с точностью
≥99.5%, остальные — в очередь разбора.

## 8. Порядок работ

| # | Шаг | Что даёт | Оценка |
|---|-----|----------|--------|
| 1 | **Включить сохранение кадров** | разблокирует всё; копится календарно | сразу, ~1 ч |
| 2 | Аудит меток; метрика по РШР + order-independent | честные весы | ~1 ч |
| 3 | **Локализация по красной маске** | чинит промах на половине кадров | ~1 день |
| 4 | Грамматика `XXXX-XX`, словарь эпюры, порядок по x | убирает невозможные ответы и Д3 | ~0.5 дня |
| 5 | Подключить `aggregate_series` + вес по качеству | гасит случайные покадровые ошибки | ~0.5 дня |
| 6 | **Трекер последовательности + сглаживание по смене** | основной прирост точности | ~2 дня |
| 7 | Флаг «не уверен» + очередь разбора | управляемость ошибок, golden labels | ~1 день |

Шаг 1 — первым и немедленно, он единственный зависит от календаря. Шаги 2-5 не
требуют новых данных. Шаги 6-8 тем сильнее, чем больше накопилось.

## 9. Принципиальные решения

- **On-prem.** Кадры не покидают завод; внешние VLM исключены. Все слои локальны.
- **Синтетика — инструмент точечный, а не основной.** Раз реальные данные теперь
  доступны, они строго лучше. Генерация нужна там, где реальных нет: цифры 3/6/7,
  редкие значения эпюры. Text-to-image «нарисуй шпалу с надписью» не подходит
  принципиально — такие модели не рисуют точный текст, а метка обязана быть верной.
- **Структура важнее модели.** Итерация номеров и словарные токены дают больше,
  чем любое дообучение. Сначала выжать структуру, потом наращивать модель.
- **Постфактум — не только минус.** Он разрешает offline-сглаживание по смене,
  которое точнее online-решения.
